# Revising a deliverable against reviewer feedback

Read this when a document, deck or report comes back with comments. It comes from two review rounds on a conference training deck in September 2026, where the drafts were built by a script and reviewed in a shared Google Drive copy.

## Before editing

1. **Collect feedback from every channel.** That means email, comment threads and direct edits in the shared copy. Direct edits send no notification. In that project a reviewer retyped nine slide titles in the shared file fifteen minutes after her email and never mentioned it. The only sign was the file's modified time and size.
2. **Diff the shared copy against your source before regenerating.** If the deliverable is built from a script, template or markdown source, a rebuild silently overwrites whatever reviewers typed into the shared copy. Extract the shared copy's text, compare it with what the source produces and port every difference back first.
3. **Read the house voice from sibling documents.** Pull 25 or more headings from the organization's other documents of the same kind. Write down the convention: phrase type, length, casing, colon patterns and how sections open and close. In that project the other sessions used Title Case noun phrases of 2 to 7 words, often "Label: Subject". None addressed the reader.
4. **Turn each feedback item into a check before editing.** Write one assertion per comment, as a test, a grep or a checklist line. That makes "addressed" provable, and a later rebuild cannot quietly undo it.

## While editing

5. **Adopt reviewer wording verbatim.** When a reviewer types a replacement, use it exactly, even when it breaks one of your own style rules. Her title "Excess Heat is a Value You Have Already Paid For" beat a "no second person in titles" rule. Drop the rule, keep her words. Where a reviewer stopped partway through, keep your versions for the rest only if they already follow the pattern she set.
6. **Fix the class, not only the flagged lines.** A reviewer who marks four lines "awkward" is showing you a register. Sweep the whole document for the same pattern.
7. **Say who each example is for.** A mixed audience reads an unframed example as random. Open each one with who it is about and who it applies to, such as "Applies to: sites with steam boilers", and label illustrative cases as illustrative.
8. **Move lines, don't delete them.** In spoken material the memorable line can live in the speaker notes. The slide states the fact and the speaker can still say the line.
9. **Leave unconfirmed specifics out.** Times, session numbers, named contacts and citations go on the page only once confirmed. Use a visible placeholder and list it as an open question.

## Before calling it done

10. **Re-check the shared copy.** Before each new round, compare its modified time and size with the version you last read. Comment notification emails cover comments only.
11. **Render it and look.** Plainer wording often runs longer and overflows boxes sized for the old copy. In that project the reviewer's titles only fit once headers could shrink to fit. Check the rendered output, not just the text.
12. **Reply per thread.** Draft one or two sentences for each comment saying what changed and where, using the new page or slide numbers.
